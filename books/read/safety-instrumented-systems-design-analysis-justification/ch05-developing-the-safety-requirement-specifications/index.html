Developing the Safety Requirement Specifications

Paul Gruhn & Harry Cheddie · ISA (2006)

Chapter 5 · 14 source pages · companion notes
Key terms. SRS — the safety requirement specification: what the system must do, and how well. · Functional requirement — the logic: which input drives which output. · Integrity requirement — the performance: how reliably that function must work. · Systematic failure — a design or process error; not quantifiable, controlled only by procedure. · Cause and effect diagram — the matrix showing which input acts on which outputs. · Management of change — the procedure that must precede any edit to an approved document.

If chapter 3 answered “why must it be a separate system”, this chapter answers “how must that system be written down”. Behind the answer sits one number worth remembering: 44 % of accidents caused by control and safety system failures come from specifications that were wrong or incomplete — not from hardware that broke. Most of the failure was written into the system before anybody installed anything.

The specification is the design

It is tempting to treat the safety requirement specification as paperwork that follows the engineering. It is the other way round. Once the SRS is approved, every later activity — the logic design, the factory acceptance test, the proof test procedure, the management of change — is checked against it. An error in the SRS therefore does not stay in one place. It propagates into the software, into the test that confirms the software, and into the procedure that maintains it, and it does so consistently, so that every check agrees with every other check and the error becomes invisible.

This is what makes a systematic failure different from a random one. A failed transmitter announces itself eventually. A specification that says “close valve B on low pressure in vessel A” when the process actually needs valve C, or needs the valve closed on high pressure, will be implemented exactly as written, tested exactly as written, and will work perfectly — until the day the demand arrives. No amount of reliability engineering addresses that failure, because nothing in the system is unreliable.

Forty-four percent is a statement about process, not about engineers

The HSE figure is often quoted as if it were a criticism of the people who write specifications. It is more useful read as a criticism of the sequence in which specifications get written. The four activities that precede a specification — conceptual design, hazard analysis, application of non-SIS layers, SIL determination — are exactly the four that get compressed when a project is late, and they are compressed in that order. The specification is then written against a design basis that was never finished.

The symptom is easy to recognise in a review: a specification that describes what the system will do, in great detail, without ever stating what it is protecting against. The document is not wrong; it is unanchored. Every sentence can be traced to an instrument tag, and no sentence can be traced to a hazard.

Simple is not a style preference

The ethylene oxide story in section 5.2.7 is usually told as a warning about software. It is better told as a warning about valve counts. Three valves in series with two bleeds between them is already a configuration whose failure modes are hard to enumerate; duplicating all five so the system can be tested online doubles the enumeration and adds a mode in which the test itself creates the hazard. The software error was the proximate cause; the configuration was the reason a software error could produce an explosion.

The practical test for a safety function is whether a competent engineer who has never seen the plant can follow the cause and effect diagram in one pass. If they need the narrative to explain it, the diagram is describing a design that is too complicated to be verified — and a function that cannot be verified cannot be claimed at a high SIL, whatever the hardware.

Cause and effect: the one document everybody reads

Of all the documents in the SRS package, the cause and effect matrix is the one that actually gets used after commissioning. The P&ID is consulted when something is modified, the narrative is read once, the logic diagrams are read by the programmers — but the cause and effect matrix is what the operator, the maintenance technician and the auditor all reach for, because it answers the only question that matters at three in the morning: if this goes out of range, what happens?

That makes its accuracy disproportionately important, and its format disproportionately conservative. One row per cause, one column per effect, one mark per action, and a notes column for everything that does not fit — delays, reset locations, permissives. A matrix that needs a footnote to explain a footnote has stopped being a matrix.
