Controller Output Modes, Equations and Cascade Control

Wolfgang Altmann · IDC Technologies (Phiên bản 3.02)

Chapter 9 · 21 source pages · 9 figures · companion notes
Key terms. Virtual output — the value the controller computes, before the limit. · Saturation — the virtual output passes the limit while the real output does not. · Initialization — the mode in which the secondary sends its set point back up to the primary's output. · PV-tracking — in MANUAL the set point is forced to the PV so the error is zero. · Equation type A / B / C — three ways of sharing PV and SP between the P, I and D blocks. · Ultimate primary — the top controller of a cascade chain.

This is the hinge chapter of the book. Before it, every controller was a black box with two inputs and one output. After it, the controller has three more things: an output block with a mode, a limit that either saturates or does not, and a set of equations that decides how PV and SP are shared between the P, I and D actions.

Those three things sound like plumbing. They are in fact the preconditions for joining two controllers into a cascade — and a cascade is the single most profitable intervention available on an ordinary control loop.

One calculation, many outputs

The first idea in the chapter is that the PID calculation is a single number per scan, but the controller may own several output blocks. Each block keeps its own absolute value, its own mode, its own limits and its own initialisation. The increment is common; the value is not.

This is what makes a cascade physically possible. The primary controller's output is not a valve position, it is a number that a secondary controller will treat as a set point. The same increment therefore has to arrive at both blocks, while the two blocks sit at completely different absolute levels — one perhaps at 35 % and the other at 72 %.

Saturation, and the two ways to handle a limit

The chapter's second idea is subtler and is where most commissioning errors live. A controller does not know its own output value; it only knows the increment it wants to apply. If the output is already at 100 %, the increment has nowhere to go, and what happens next depends entirely on how the limit is implemented.

Under saturation, the controller keeps a virtual output that is free to exceed the limit. The real output stays pinned, but the virtual one keeps accumulating. When the disturbance finally reverses, the controller has to unwind all of that accumulation before the real output moves at all — which is why a loop that wound up during a start-up can take minutes to come back. Under non-saturation, the calculation is done on the real value only, the excess is discarded each scan, and the loop responds as soon as the error reverses.

Figure 9-7 is the picture to keep. Both controllers reach the ceiling at the same moment. The one that saturates stays there long after the disturbance has turned around, because its virtual output has to be spent down first. The one that does not saturate comes off the ceiling immediately. Neither is wrong as an implementation; they are different answers to the question of whether the controller is allowed to remember what it could not deliver.

Cascade: putting the fast loop inside the slow one

The feed heater example is the canonical one and worth following closely. With temperature control alone, the valve position is the controller's output, and a change in fuel supply pressure changes the heat input without the controller knowing anything has happened until the outlet temperature moves. With a flow loop inserted, the valve is now the flow controller's business, and the temperature controller asks for a flow rather than a valve position.

The physics that makes this work is the difference in speed. A flow loop settles in a second or two; a heater's outlet temperature takes minutes. A disturbance that acts on the fast variable is invisible to the slow controller until it has propagated all the way through the process, by which time it is a large error. Interposing the fast loop means the disturbance is corrected before it ever becomes an error in the slow variable. That is the whole of cascade control, and the rest of the section is bookkeeping needed to make it bumpless.

PV-tracking and initialisation: the two mechanisms that prevent the bump

A cascade is easy to build and hard to switch on. The difficulty is that when the secondary goes to automatic, its set point must already equal the value the primary wants to command, and the primary's output must already equal that same value. Two mechanisms achieve this, and they are easy to confuse.

PV-tracking acts inside one controller: while it is in manual, its set point is forced to equal its measurement, so the error is zero and the integral does not wind. Initialisation acts between controllers: the secondary sends its set point back up the chain into the primary's output block, so that when the primary later goes to automatic it starts from exactly the value the secondary is already using. The first prevents a bump inside a loop; the second prevents a bump between loops.

Equation types: who gets to see the set point

The last conceptual section answers a question that rarely gets asked aloud: when the operator moves the set point, should the proportional and derivative actions see it? Under type A they do, and a large set-point step produces a proportional jump and a derivative spike in the same scan. Under type C they do not — P and D act on the measurement only, and the error feeds only the integral, so a set-point step becomes a ramp.

Figure 9-6 draws the alternative. The difference is not academic: on a large set-point step the type A controller produces a proportional jump plus a derivative spike in the same scan, which is a step change commanded into the valve; the type C controller ramps into it instead.

The algebra in the chapter proves that with a constant set point the two types are identical, which is the important reassurance: choosing type C does not change how the loop rejects disturbances. It changes only how the loop follows the set point. That is precisely the distinction a cascade needs, because the primary's set point is a process value and the secondary's set point is a command.

The rule that follows is short and worth memorising. Secondaries must use type A — using type C there would leave only the integral acting between the primary's output and the secondary's output, adding ninety degrees of phase lag to the primary loop and destabilising it. The ultimate primary is the natural home for type C, because that is the controller whose set point an operator can move, and the one whose output drives a valve that should not be slammed.

Tuning a cascade

Tune from the inside out. The secondary is tuned first, with the primary left in manual, because the secondary has to be fast and stable before it can be treated as part of the process. Then the primary is tuned with the secondary in automatic, treating the whole inner loop as one more lag in the process. Tuning in the other order does not work: the outer loop would be tuned against a process that changes the moment the inner loop is closed.

The chapter's note that the secondary gain should be below one is easy to miss and matters. If the secondary's gain is above one, the primary's full output range is not passed through to the secondary's output, and the cascade loses authority at the extremes exactly when it is needed.

One primary, several secondaries

Section 9.10 is the case that breaks a naive implementation: a control strategy in which the primary controller owns more than one output calculation. The PID result is the dynamic output of the primary — the CV computed once per scan — and in a digital controller that single number is used to increment each output block independently. Because the blocks can sit at different absolute values at any moment, each has to be incremented separately rather than written.

What this buys is scale without extra logic. One temperature controller can drive three fuel valves, or a pressure controller can trim two compressors, and the primary never needs to know how many secondaries it has — the increment is common and each block resolves it into its own engineering units. What it does not buy is permission to mix quantities: the outputs must all mean the same thing, or the primary's single increment means something different at each block and the cascade has no common variable to regulate.
